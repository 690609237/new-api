一、项目总览

围绕患者离院后的康复训练、饮食记录和恢复随访，建立患者在家执行、医护在线跟进、必要时复诊的持续服务。一期先形成照护闭环；二期在此基础上增加院方服务相关的商品销售、订单履约与售后。

范围一期拟建设二期拟增加
患者服务今日任务、长期计划、记录、医护消息与周报及摘要商城、商品详情、订单、支付、物流与售后
医护工作台建档、计划、内容库、模板、待办处置、复诊安排及周报复核商品维护、订单处理、售后申诉及支付配置
AI 辅助限定动作识别、餐食候选识别、反馈整理与摘要辅助沿用一期能力，不默认增加商品推荐或自动售后裁决
基础服务正式账号、数据保存、权限隔离、日志和备份支付与退款回调、订单审计及交易对账基础能力

1.1 范围口径

本文描述预计开发的业务范围，不代表现有原型已经接入真实 AI、医院系统、支付或物流。原型页面和数据用于沟通流程；正式视觉样式、字段及操作细节仍需设计确认。正式系统所需的账号权限、数据安全和支付核验属于上线配套能力。

二、主要功能

2.1 患者端服务

由医生完成患者服务建档后，患者端围绕当天计划、任务执行、执行反馈和问题沟通跟进形成闭环。尚未发布计划时，患者看到等待医护设置，不自动生成 V1 计划；患者仍可提交不适或需要帮助的反馈。

→
02完成居家任务康复训练、餐食拍照、恢复随访
→
03核对并提交确认识别结果，补充实际情况

04获得后续跟进查看医护反馈，必要时主动反馈

今日与消息查看当日任务、医护重要反馈、未读消息及复诊安排只有医护新反馈触发对应提醒；查看或关闭提示不关闭待跟进事项
长期计划查看医护设定的起止时间、周期目标、回访间隔及过去与未来分段时间进度不等于恢复进度；回访日期不等于已完成回访或已挂号
康复训练进入独立训练页，查看动作与组次；按全天总量或指定时段执行并确认实际完成量未安排时段不产生训练要求；只覆盖双方确定的适配动作
饮食记录查看全天或分餐参考搭配，按早餐、午餐、晚餐记录食物、份量及实食情况饮食记录主要作为医生后续跟进和调整计划的辅助判断
恢复随访完成问答、补充恢复情况与执行困难；随时主动反馈不适紧急情况先提示就医，不承诺线上实时监护
进度与我的查看历史记录、计划版本、周报及摘要、服务团队和服务边界患者不能自行修改医护计划、处方或关闭高风险事项

2.1.1 正常执行与异常反馈

患者进入当天计划 → 完成训练、饮食或随访记录 → 核对识别结果并提交 → 工作台形成记录；出现不适、执行困难或需核实情况时，生成医护待处理事项。识别结果只用于总结和摘要，不提供医疗建议，不能作为临床事实。

2.1.2 训练和饮食的不同记录口径

训练：全天量代表一天合计；也可只安排上午，不要求下午和晚间都有动作。不因计划改版要求患者重复完成已经执行的训练。

饮食：计划可仅设置全天量或某一餐，空餐次不代表禁食。实际摄入仍按三餐分别记录；没有吃可说明原因，不通过补吃完成打卡。

页面中的训练组次、能量、风险阈值及服务时段均不能直接沿用演示数据，正式口径由院方制定计划并审核确认。

2.2 医护端服务

2.2.1 医护建档与计划制定

医生先建立患者服务档案，再从档案进入建立计划阶段。建档不等于计划已生效，首次经医护核对发布后才生成 V1 并向患者下发任务。

01 就诊或出院核对患者与服务来源
02 建立档案确认授权和负责团队
03 配置计划设置周期、内容与执行量
04 核对发布生成版本并下发患者
功能拟支持内容必须由谁决定
患者服务档案维护服务路径、就诊事项、负责团队及授权状态；从档案进入建立计划入组医护核对身份、适用服务及知情说明
阶段计划选择训练、饮食、恢复随访；设置名称、目标、注意事项及个体限制负责医护确认，不能由 AI 自动发布
周期与回访设置起止日期、持续天数、回访间隔；患者看到对应长期分段医护根据患者情况确定周期，不由系统自动延长
训练安排从动作库选用，按全天总量或指定时段搭配组数与每组次数医护核对动作适用性、限制和训练量
饮食安排从食材库选用，设置全天或分餐份量，查看碗杯换算和参考能量医护或营养师确认食材、份量、过敏及耐受限制
常用模板新建、编辑、复制、归档，保存搭配与相对周期；套用后个体化调整医护维护个人模板，每次套用仍需核对
调整与版本填写调整原因、核对发布新版本；历史记录绑定提交时的计划授权医护确认生效和衔接，不追改既有记录

2.2.2 计划能力说明

一期重点支持医生制定周期计划、患者按日执行并提交反馈，医生根据记录进行跟进和调整。变更当日的任务衔接以“不重复训练、不篡改历史”为原则；正式生效时点与确认流程需院方在需求评审中确定。

2.2.3 动作库、食材库与模板维护

内容库是医护制定计划的基础资料，不是系统自行产生的处方。普通医护可查看、选用和搭配；只有具备内容管理权限的管理员才能新增、编辑、停用和更新动作库、食材库，专业人员负责审核内容口径。

内容主要维护字段院方维护责任
动作库名称、分类、计量单位、适用说明、限制与注意事项、启停状态及版本康复专业人员提供并审核；内容管理员录入维护。示范素材与识别适配清单单独确认
食材库食物名称与状态、单位、过敏提示、克数与碗杯换算、容器大小、能量基准及来源营养师核定数据口径和误差说明；管理员维护，不使用未经核验的演示系数
常用计划模板训练与饮食搭配、服务周期、回访间隔、目标和注意事项医护维护个人常用模板，不包含患者身份和执行记录

2.2.4 计量与版本规则

除克数外，提供小碗、杯、勺、个等生活化参考，并配套容量、碗口直径、高度和装盛方式。同一个容器装不同食材，对应克数可能不同，不能直接按容量换算重量。

缺少能量依据时显示“未知”，不当作零，也不自动补齐。库修改不自动覆盖已发布计划，医护采用新版后需重新核对。

2.2.5 人工跟进与复诊摘要

医护工作台围绕待处理事项组织工作。系统帮助把需要关注的情况送到队列，最终处置、计划调整、复诊建议和高风险关闭均由授权医护负责。

工作环节主要功能责任边界
认领与处置查看患者原始记录、识别来源和不适描述，认领事项并填写处置依据可转为跟进中、待患者补充或待复诊；患者补充信息回到原事项，保留历史
复诊与关闭记录复诊安排并关联具体事项不等于号源预约成功；高优先级事项必须经授权医护复核，AI 和患者均不能自动关闭
周报及摘要汇总执行记录、缺失信息、处置进展和复诊待讨论问题先形成草稿，再由医护复核发布；重新生成需重新审核，不自动抹去未解决问题
系统服务可持续运行，但人工跟进仍按院方约定服务时段进行。缺失记录、完成打卡或周报发布均不表示恢复正常。

2.3 商城（二期）

二期增加围绕院方居家服务的自愿消费入口，复用一期的患者与角色体系，建立独立商品和交易记录。商品销售不代替医学适用性判断。

2.3.1 商品库与患者商城

功能二期拟支持责任与限制
商品库营养餐、减脂餐、医疗器械或穿戴设备、保健器械、训练课程分类展示院方或授权运营方核验资质、来源、供应与适用说明
商品维护名称、说明、单一规格、实物或线上服务、价格、库存或名额、售后政策及上下架仅管理员维护；普通医护只读，不默认具有订单与资金权限
患者商城分类、搜索、详情、使用说明、价格与售后说明；提供我的订单入口只展示可售商品，不自动按疾病推荐商品
确认下单选择数量、填写收货信息、确认自愿购买，创建待支付订单并锁定价格快照原型基线为单笔一个商品，不含购物车、多规格、促销或拼单
课程服务付款后开通对应服务记录，不填写物流不默认包含视频制作、完整课程播放平台或学习效果评估
支付入口微信支付及支付宝渠道展示、启停配置与支付结果处理正式上线依赖合法商户签约和服务端支付接入；前端结果不能作为收款依据

2.3.2 患者购买路径

商城 → 分类或搜索 → 商品详情 → 阅读适用与售后说明 → 确认订单 → 支付 → 查看配送或服务开通 → 确认收货或服务完成。未付款可取消，未发货实物可修改收货信息。

2.3.3 与照护服务的界线

服务与消费分开：商品购买独立记录，不影响照护计划的发布、执行与医护跟进。
计划独立：购买营养餐不会替代实际摄入记录；购买课程或器械不会自动加入训练计划，也不自动获得医护适用性确认。
设备销售不等于设备接入：蓝牙连接、实时监测、设备数据回流和医学报警不默认纳入。

2.3.4 订单履约、退款与申诉

订单状态由实际业务动作推进，不允许仅靠随意修改状态完成收款、发货或退款。患者只查看本人订单，管理员根据职责处理履约和售后，并保留过程记录。

场景主要状态流转人工动作
实物订单待支付 → 待发货 → 已发货 → 已完成管理员填写快递公司和单号，可更正物流；患者确认收货
线上服务待支付 → 服务已开通 → 已完成按订单规格交付，患者确认服务完成；不走快递流程
取消订单待支付 → 已取消患者取消，释放预留库存；不产生退款
未发货或服务退款申请售后 → 待审核 → 待退款 → 已退款管理员核对原因、服务使用情况及退款金额
实物退货审核同意 → 待寄回 → 待收退货 → 待退款 → 已退款患者填写退货物流，管理员收货检查并确认退款
驳回与申诉审核驳回 → 患者补充说明 → 申诉待复核 → 再次处理驳回须说明理由，申诉交人工复核并留痕

2.3.5 管理员订单管理

按订单状态和售后状态筛选，搜索订单号或商品，查看商品及价格快照、收货信息、支付结果、物流和处理历史。普通医护不默认查看收货地址、交易及退款信息；正式岗位权限按院方授权设置。

2.3.6 支付、退款和售后边界

付款失败保留待支付状态，退款失败保留待退款状态并可重试。正式系统需防止重复扣款、重复退款和重复释放库存，并核对支付渠道回执。现阶段基线支持整单售后，不含部分退款、换货或多商户争议分账；鲜食、已使用课程、已拆封器械应按品类单独制定政策。

订单物流基线是人工维护运单信息，不含实时轨迹查询。开票、运费、配送区域、售后时限和退款到账时效须另行确认。购物投诉不替代身体不适反馈通道。

2.3.7 商城与配置入口位置

商城在患者端 App 底部导航设有独立入口，与今日计划、记录等照护功能并列；商品维护、订单处理、售后申诉与支付配置集中在医护工作台的商城管理菜单，仅具备权限的管理员可见和操作。

患者端在饮食记录等页面可预留推广商品展示位（图 9 位置仅为示意），仅展示已上架商品并带明确标识，与照护内容明显区分；具体展示位置、频次与关闭方式由院方确认。

三、部署方案

3.1 AI 辅助功能与调用方式

动作识别等能力在接入阶段一次性完成适配与验证；餐食识别、随访整理和周报及摘要在使用中例行调用大模型，按调用量持续产生费用。是否采用大模型，还需结合识别准确率、数据合规和部署方式确认。

能力AI 可以辅助的内容调用方式与计费属性人工与失败兜底
动作识别对适配动作进行姿态检测、计次和基础执行提示一次性接入与适配验证；专用视觉算法、授权费或算力费，不必使用大模型机位或遮挡导致不可评估时明确提示，允许自报和人工核实；不评价诊疗效果
餐食识别从图片给出食物候选，辅助记录和匹配已核定食材例行按量调用：多模态模型按图片、输入输出量或请求量收费患者核对食物与实食量；无法识别可手动记录，不承诺照片精确测重
随访信息整理整理患者描述、提取需关注线索，辅助呈现待核实信息例行按量调用：结构化问答可不调用模型；启用文本理解时按调用量收费危险选项先走院方审核规则；模型不可替代临床分级或自动结案
周报及摘要根据已保存记录整理执行、缺失和未解决事项例行按量调用：大模型按输入输出用量收费医护核对来源后发布；模型不可补写患者未提供的事实或诊断

3.1.1 必须守住的四条边界

边界明确规则
不自动诊断结果只作为记录和待核实线索，不输出“恢复正常”“可以停药”等临床结论。
不自动改方案AI 不改处方、训练量或饮食方案，不代替医护发布计划。
不自动关闭高风险模型、患者打卡和购买行为均不能关闭高优先级医疗事项。
不因模型中断丢失服务识别失败或调用超限时保留手动记录与医护跟进，显示不可评估或待处理。
正式识别范围、样本验证、性能及失败判定需单独验收。照片、视频或健康文本是否可发送至外部模型，必须先完成院方数据合规与授权确认。

建议采用院方认可的专有业务环境，并按需调用 AI 服务。以下为部署服务必需的资源组成；患者和医护通过受控入口使用同一套业务服务，数据集中保存，不能以个人浏览器的本地存储替代正式服务。

3.2.1 两种落地方式

院方认可的云环境：部署稳定业务服务、数据库和文件存储，按授权调用外部 AI；适合快速试点并按使用量扩展。
院内或专有环境：按院方网络与数据要求部署。若健康数据不得出域，应采用批准的院内或专有模型；通常增加算力、授权和运维成本。

以上是逻辑服务组成，不代表每项都要购买一台服务器。具体配置、并发、存储容量、可用性和恢复目标在试点规模及媒体策略确认后测算。系统全天可用不等于医护全天在线。

二期：商品资料与资质、价格库存、配送能力、分品类售后政策、销售与收款主体、支付商户资料及退款授权规则。

六、预计研发周期

以下为当前范围下的研发周期预估，实际排期取决于院方资料准备、专业审核、接口条件和试点反馈。周期用于项目计划沟通，最终以双方确认的实施计划为准。

阶段预计周期主要工作内容
一期照护闭环约 8—12 周患者端当天计划、周期计划、训练与饮食记录、问题沟通；医护建档、计划、内容库、待办和周报；完成基础 AI 能力验证与部署。
院方素材与审核约 2—4 周，可并行准备动作、视频、食材、份量和能量依据；明确内容管理员、专业审核人、计划制定人及人工跟进规则。
二期商城与订单约 6—10 周商品库、患者商城、订单、支付渠道、物流信息、退货申诉、退款及管理员权限；周期与一期试点结果衔接。
联调、试点与验收约 2—3 周真实样本验证、权限核验、AI 失败兜底、支付和售后异常演练、培训、问题修正和上线确认。
