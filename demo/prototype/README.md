# 新华在家｜院后持续照护交互原型

用于和院方一起评审「患者记录 → 医护接管 → 反馈 / 调整 → 复诊摘要」是否闭环。纯前端、全量虚构数据，不用于临床决策，也不代表已确认的医院服务规范。

## 打开方式

不需要安装依赖。在项目根目录启动静态预览：

```sh
python3 -m http.server 4173 --bind 127.0.0.1 --directory prototype
```

- 患者端：`http://127.0.0.1:4173/#patient`
- 医护端：`http://127.0.0.1:4173/#doctor`
- 顶部按钮随时切换两端；「流程走查」提供演示路径，「待细化问题」集中展示待讨论规则。
- 可以直接打开 `index.html`，但建议使用上述静态预览，确保本地存储与跨标签页联动行为一致。
- 此服务仅提供静态文件，不含业务服务端。地址只供当前电脑访问，不是公开分享地址。

## 产品形态

### 患者端：以每日任务为主，不以聊天为主

| 页面 | 主要操作 | 向医护端传递什么 |
| --- | --- | --- |
| 今日 | 查看阶段计划、训练、饮食、恢复问答、反馈不适 | 患者确认后的记录和待处理事项 |
| 计划 | 查看整个康复 / 观察周期、周期目标、当前分段、计划回访和复诊节点 | 由医护设置周期，患者只读，不自行延长或调整 |
| 进度 | 查看记录来源、计划版本、周报 | 为复诊保留执行过程，而非生成诊断 |
| 消息 | 查看医护回复、计划更新、复诊安排；向原事项补充信息 | 补充材料回到原事项，保留责任人和历史 |
| 商城 | 自愿查看餐食、器械、课程，创建模拟订单、付款、查看配送及申请售后 | 独立订单信息，不进入临床计划或自动改变处方 |
| 我的 | 查看服务团队、计划、复诊日期、服务边界 | 明确谁提供服务及何时响应 |

三个功能模块分别是：康复训练陪伴、饮食记录、恢复随访。AI识别均由预置结果模拟，患者可以核对和修正；不调用真实模型。

### 医护端：以事项处置为主，不以数据大屏为主

| 页面 | 主要操作 |
| --- | --- |
| 照护总览 | 查看优先级队列、筛选 / 搜索、认领、查看原始反馈、记录处置 |
| 患者档案 | 建档、确认服务授权，随后进入建立阶段计划；查看关联记录、切换患者视角 |
| 阶段计划 | 设置康复 / 观察周期、目标和回访间隔，人工调整任务、说明原因、审核发布新版本 |
| 照护内容库 | 动作库、食材库、商品库；普通医护只读商品，管理员维护商品、价格、库存、上下架 |
| 订单与售后 | 仅管理员：订单筛选、快递发货与运单更正、售后审核、申诉复核、收退货及模拟退款 |
| 模拟支付设置 | 仅管理员：商户展示名、渠道开关、支付 / 退款成功或失败演示，不接入真实网关 |
| 恢复周报 | 生成记录快照、核对并发布；保留未解决事项 |

## 建议的 10 分钟走查

1. **入组与计划**：医护端「建立服务档案」，填写虚构资料并确认授权。此时不产生 V1，也不派发任务；成功页可选择「建立阶段计划」或「稍后设置」。完成内容与周期配置、人工核对并发布后，才生成 V1。
2. **执行**：切换患者端，从患者姓名按钮选择档案。完成训练或饮食记录，核对模拟结果，再保存。切换医护端检查记录是否同步。
3. **异常**：患者在训练中选择停止并反馈，或在恢复问答中选择明显 / 紧急不适。应立即看到线下求助提示，不必先填写长篇描述。
4. **人工跟进**：医护在队列中认领事项，填写回复，选择「待患者补充」；患者在消息中补充后，应回到同一事项，不重复创建待办，且不丢失责任人。
5. **调整 / 复诊**：从事项进入计划调整或复诊安排，返回后未保存的处置文字应保留。新计划需要人工确认，历史记录保留原版本。选择「待复诊」前必须先为该事项关联模拟复诊安排。
6. **总结**：生成周报、医护审核发布，再回到患者端查看。之后新增记录不会静默修改旧快照；发布周报不会自动关闭未解决事项。

### 额外异常路径

- 训练选择「画面遮挡 / 机位失败」：即便患者自报完成全部次数，也应记录为不可评估，而非成功识别。
- 饮食选择无法识别 / 手动填写：不把未知餐食虚构成精确营养值。
- 未认领直接保存处置：应要求明确责任人。
- 高优先级事项直接关闭：应要求处置说明和人工复核确认。
- 患者再次提交「无新增不适」：不能自动关闭既有高风险事项。
- 今日任务全部完成但仍有重要事项：患者首页仍提示待跟进；完成率不代表恢复正常。

## 状态与数据约定

### 长期计划视角（本次新增）

- 患者底部新增「计划」入口，今日首页也提供「查看整个康复计划 / 观察周期」快捷入口。
- 医护在「阶段计划 → 查看 / 调整计划」设置周期类型、开始日期、结束日期、周期目标和回访间隔。
- 整体周期开始日期独立于版本生效日。调整当天任务产生新版本，但不会把已进行的第 8 天重新变成第 1 天。
- 按医护设置的 N 天划分回访段，第 N 天为该段计划回访日；最后不足 N 天的一段在周期末回访。不是自然周，也不是临床治疗阶段。
- 可以查看过去、当前、未来分段，过去显示实际提交记录，未来仅展示已发布计划及待确认提示。回访日期已过不代表已回访，时间进度不是恢复评分。
- 实际复诊安排单独显示在所属分段内，不把每个周期回访误当成到院复诊。
- 周期未开始或已经到期，今日页不派发周期任务，仍可主动反馈和查看记录；不自动续期、结案或关闭事项。
- 旧版本本地数据保留原始周期起点。未设置回访频率和周期目标时，明确提示待医护补充，不悄悄生成已获医护批准的节点。
- 本版支持单个周期最长 366 天，回访间隔 1–90 天。这里只规划回访日期，尚未生成自动提醒、回访完成记录或逾期任务。
- 本轮演示将林阿姨设为 **2026-10-01 至 2026-11-11，共 42 天，每 7 天回访**。其他浏览器及重置后的数据仍按初始模板展示。
- 后续需确认：不同分段能否提前设置不同任务、节假日调整、不规则复查日期、每个回访节点的完成 / 延期状态、连续多个周期的历史归档。

### 通用状态

- 事项主要状态：待处理 → 跟进中 → 待患者补充 / 待复诊 / 已关闭。
- 患者对未关闭事项补充情况后，回到跟进中；已有复诊安排仍保留。此状态策略需要院方评审。
- 原型不提供患者关闭事项或 AI 自动关闭事项的入口。
- 计划发布后产生新版本；历史记录绑定提交时的版本。
- 当天改计划不会重置此前已确认完成状态，避免原型强迫患者重复训练；正式规则仍待确认。
- 数据只保存在当前浏览器、当前来源的本地存储，键名为 `xinhua-care-prototype-v1`。
- 同一浏览器、同一来源的标签页可以联动；不同浏览器或设备不能共享，不具备真实多用户并发和权限隔离。
- 演示业务日期固定为 **2026-10-08**；记录显示的时分为操作时的北京时间，不代表真实病历时间。
- 初始包含 4 位虚构患者。验收浏览器可能保留本轮走查记录；可自行使用「重置演示」恢复初始场景。
- 仅内存保存尚未提交的处置草稿，刷新页面可能丢失未提交内容；已保存数据刷新后仍在。

## 安全边界与未接入能力

- AI不自动诊断、不自动改处方、不自动发布临床计划、不自动关闭高风险事项。
- 紧急反馈展示即时求助提示，不承诺线上实时接管。页面中的服务时段和优先级时限均为演示。
- 风险分流由明确的选项和预置规则演示；自由文本没有真实临床语义识别能力。
- 热量、蛋白质、动作次数、摄入比例阈值、随访问题均为展示数据，不是院方确认的医疗标准。
- 未接入相机、麦克风、真实AI、通知、医院系统、挂号、支付、身份认证、真实角色权限或临床审计存储。
- 「安排复诊」只创建本地模拟安排，不代表已预约成功。
- 不要录入真实姓名、联系方式、患者照片、检查单或真实病历。

## 院方评审时优先确认

| 待确认问题 | 当前处理 | 下一步需要决定 |
| --- | --- | --- |
| 谁接单、多久处理、超时怎么办 | 模拟一名授权医师；不做真实告警 | 首接角色、跨科转交、值班与升级规则 |
| 什么情况停止任务或必须复诊 | 明确不适时给出提示，医护人工处置 | 按术种 / 阶段审核任务、禁忌和风险阈值；人工暂停 / 恢复计划的流程 |
| 改计划当天算不算完成 | 保留完成状态和原记录版本 | 生效时间、补任务规则、患者确认，避免重复训练 |
| 识别失败和信息缺失如何处理 | 不计为AI成功，允许自报 | 重拍、人工核实、连续失败和失联的兜底 |
| 家属如何参与 | 尚未实现代办 | 授权范围、填写人身份、消息接收人及撤销授权 |
| 提交错了如何更正 | 仅支持提交前修改 | 更正申请、原始证据保留、医患双向确认 |
| 复诊安排何时算闭环 | 本地安排关联事项；仍保留待办 | 号源确认、改期、未到诊、到诊后记录回流 |
| 周报是否应自动更新 | 单份最新快照，手动重生成 | 历史版本、发布与已读、复诊前冻结、更多原始记录；当前明细仅显示最近6条 |
| 老年患者是否看得清、点得准 | 手机布局与短流程原型 | 真机大字号、语音、误触、弱网和家属协助的可用性测试 |

## 本轮患者交互调整

- 今日页头像复用“我的”的头像、姓名排列与间距。
- 医护新反馈位于完整康复计划入口之前，只显示未查看、未关闭的医护消息；系统回执不触发。常规、重要、紧急分别使用铃铛、旗帜、警示图标与文字；事项回复继承事项优先级。
- 查看仅标记本条已读；叉号仅关闭本条首页提示，消息仍在消息页，医疗事项状态不变。有多条时先显示最高优先级，处理一条后显示下一条。旧消息没有优先级时显示常规，不推测临床风险。
- 康复训练、饮食记录、恢复随访改为患者端独立内容页，包含任务总览、记录步骤和返回入口，不再借用弹窗。
- 饮食分早餐 / 午餐 / 晚餐独立保存，三餐都有确认记录才算当天饮食任务完成；没吃可记录为 0%，触发原有模拟核实流程。
- 训练按每日组数拆至上午 / 下午（单组只显示上午），总组数不变；这是原型时段示例，具体时段配置仍需院方确定。未评估 / 部分完成不算时段完成，已完成时段不重复派发。
- 旧版整日训练完成记录继续有效，避免重复训练；旧版无餐次饮食记录保留，但不推定三餐均完成。已保存记录不覆盖、绑定原计划版本。
- 本轮不实现记录更正、未提交草稿跨页保留、真实拍摄或服务端同步。
- 本轮验证：早餐单独保存与必填校验、上午训练独立完成、紧急随访提交、系统回执不触发首页提醒、医护接管后显示紧急提示、查看和叉号关闭提示但保留事项。手机 390px 下首页、三餐页和确认表单无横向溢出；首页与“我的”头像 / 姓名横坐标一致。

## 医护内容库与计划搭配

- 工作台新增「照护内容库」「常用计划模板」及独立计划编辑页。普通医护可浏览库、选择搭配、维护个人模板及发布患者计划；右上角切换「医护 + 内容管理员」后可新增、编辑、停用 / 启用库内容。这是演示权限，不是真实鉴权。
- 动作库记录名称、分类、单位和注意事项；食材库另含过敏 / 耐受提示。停用条目不可用于新发布，已发布计划不会被后台库修改自动覆盖。
- 训练按动作配置全天总量或上午 / 下午 / 晚间、组数和每组次数；饮食按全天总量或早餐 / 午餐 / 晚餐搭配食材及份量，餐次可留空。患者任务页读取发布后的安排，计划食材不等于实际摄入记录。
- 模板支持新建、编辑、复制、归档及从患者草稿另存。模板只保存内容、相对持续天数、回访间隔，不携带患者身份、具体执行日期或记录；套用后仍需个体化确认。
- 患者计划可设置开始 / 结束日期、持续天数、回访间隔及目标。修改持续天数会同步结束日期。发布须填写调整原因并人工确认，生成新版本和患者通知，不关闭任何待处理事项。
- 发布内容和库版本以独立快照保存。库更新后，编辑旧计划会提示重新采用当前版本并核对；过时或停用条目会阻止新发布。另一标签页已发布较新计划时，旧草稿不得覆盖。
- 今日若已有旧版本训练记录，新版训练从明日起执行，原记录保留，不把新任务标记为完成，也不要求患者重复补做。这是保守的原型规则，需要院方确认。
- 草稿仅在当前页面会话保留，刷新会丢失；已发布计划、模板、库内容保存在浏览器本地。同源标签页可联动，文件直开和 HTTP 预览的数据互不共享。

### 建议走查路径

1. 切换管理员，在内容库新增一个演示动作或食材；切回普通医护，确认只有查看和选用权限。
2. 在常用计划模板中新建搭配，配置动作时段、三餐和相对周期，保存模板。
3. 给虚构患者套用模板，按个体情况调整持续天数和份量，填写原因、核对后发布。
4. 切至患者端，检查长期周期、动作任务与每餐计划；提交模拟记录，回医护端查看。
5. 修改库条目，检查旧患者计划仍保留原快照，重新发布前须人工采用新版并确认。

### 尚需业务确认

- 当前一个周期使用同一套每日安排；按星期、分阶段递进、休息日及自动切换尚未实现。
- 饮食启用后至少配置一项食材，可仅设全天量或指定餐次，不强制配齐三餐；未配置不代表禁食。同一食材不可同时配置全天量与分餐量，避免重复计量；不同食材可混合配置。禁食、管饲、加餐等特殊路径仍需单独设计。
- 当前只支持即时发布，不支持未来版本预约生效；变更当日已执行任务如何衔接需院方明确。
- 模板目前为医护个人常用模板；科室共享、审批发布、内容管理员与临床审核人的边界待确认。
- 动作视频、医学适用性审核、权威营养数据库和真实权限均未接入；演示内容不能用于真实诊疗。

## 食品份量与能量参考

- 食材库增加生活单位（小碗 / 杯 / 个等）、一单位对应数量、容器容量、尺寸和装盛说明、食物状态、能量基准与参考来源。仅内容管理员维护，普通医护查看并选用。
- 克数与碗数按每个食材单独换算，不把容器 mL 当作重量 g。同一个 250 mL 示例小碗，米饭与西兰花可以有不同的装盛重量。半份 / 一份图示只帮助理解份数，不按实物尺寸或容积比例绘制。
- 计划编辑中支持按 0.5 / 1 / 1.5 / 2 生活单位快捷填量，手动修改克数 / 原计量数值时，等价份数与能量即时更新。模板、计划版本保留完整换算快照。
- 患者每餐看到原计量数值、约几碗 / 杯、参考 kcal，以及可展开的大小对照和口径。每餐和每日仅合计已配置的食材，不代表完整膳食或真实摄入，不用于判定营养达标。
- 示例系数全部为 mock，未经营养数据库校验，明确标为“原型模拟系数，未经营养数据库校验；上线前由院方营养师核定”。来源字段不等于临床审核。正式使用前必须由院方确认食品状态、营养来源、容器与误差范围。
- 能量基准与 kcal 可一起留空；未知不当作 0，部分缺失时提示“不完整合计”。此轮不改变现有实际饮食记录的模拟套餐流程，计划不会自动代填实食记录。
- 仅原始、未编辑过的种子食材自动增加参考字段并升级库版本；已有患者计划、模板快照不回填或覆盖，需医护采用新版后重新确认。自定义条目不会按名称猜测换算数据。
- 已验证：半碗 / 一碗半换算、克数反算、每餐和每日参考合计、缺失能量不当作 0、非法基准拦截、旧快照保留、重新选用后发布到虚构患者。患者午餐展开大小对照后，在 390px 视口下页面及手机内容区均无横向溢出；浏览器未见错误日志。

## 商品、订单与售后原型

### 入口与边界

- 医护工作台「照护内容库 → 商品库」，普通医护仅查看；顶部切换为「医护 + 内容管理员」后，可新增、编辑、上下架商品，并进入「订单与售后」「模拟支付设置」。订单和支付页面本身也检查演示身份，不只隐藏菜单。
- 患者底部新增「商城」，「我的」增加商城与订单入口。未发布照护计划的患者同样可查看商城；不同患者只能在界面查看和操作本人的订单。
- 商品涵盖营养餐、减脂餐、医疗器械 / 穿戴设备、医疗保健器械、训练课程，均为虚构样例。商品记录规格、交付方式、价格、库存 / 名额、适用限制和售后说明。
- 商业流程与照护流程隔离：购买不自动修改计划、不自动推荐医疗适用性、不影响不购买者的原有照护服务，也不关闭临床高风险事项。
- 首次初始化新增商城模块时，提供待发货餐食订单、已发货且待审核售后的器械订单、已开通课程订单，便于直接走查。已有模块数据不覆盖；既有患者、计划及临床记录不修改。

### 主流程与状态

1. 患者选商品 → 查看适用及售后说明 → 确认自愿购买 → 创建待支付订单。单笔一个商品，实物数量 1–10；线上课程每笔仅为当前患者开通一份。下单锁定商品快照与价格，并预留库存。
2. 待支付 → 模拟付款成功 → 实物进入待发货，课程直接进入服务已开通。失败仍待支付，可重试；待支付也可取消并释放库存。关闭支付渠道不自动取消已有订单。
3. 实物待发货 → 管理员填写快递公司与运单 → 已发货 → 患者确认收货 → 已完成。待支付 / 待发货可修改虚构收货信息；已发货可由管理员更正运单，无真实轨迹查询。
4. 课程不要求收货地址、不允许发货；患者可确认服务完成。原型没有真实视频与课程履约系统，退款后显示服务权益关闭。
5. 已付款订单可申请整单售后 → 管理员审核。未发货或线上服务同意后进入待退款；已发货实物同意后进入待寄回 → 患者填写退货运单 → 管理员确认收到退货 → 待退款。
6. 退款模拟成功后订单及售后均标记已退款；失败保留待退款可重试。未发货的库存可释放；退回实物不会自动重新上架，须管理员检查后手动调整可售库存。
7. 驳回必须填写具体理由；患者可补充说明提交申诉，回到管理员复核。订单保留处理过程，不能直接任意选择终态跳过支付或退款步骤。

### 快速走查

- 管理员在商品库编辑一项商品；患者查看详情，下单并选择微信 / 支付宝模拟付款。管理员查订单、发货；患者查看运单、确认收货、申请售后。
- 管理员先驳回并说明理由；患者补充申诉；管理员同意退货，患者填写退货物流，管理员收退货并退款。
- 在模拟支付设置中将付款或退款结果切为失败，再走一遍失败 → 改为成功 → 重试。不得出现失败后已付款 / 已退款或重复释放库存。
- 切为普通医护确认无法查看订单或修改支付设置；切换另一患者确认看不到前一患者的订单。

### 待院方细化与技术限制

- 需明确实际销售 / 收款 / 开票主体、商品资质审核、供应与配送范围、餐食配送时段和冷链、分品类售后政策、退款审批责任及申诉响应期限。
- 后续设计购物车、多规格、多商户、优惠、运费、支付超时、部分退款、凭证附件、售后撤回、客服通知与课程有效期 / 观看进度；本版暂不实现。
- 支付设置只保存模拟商户展示名称、微信 / 支付宝开关及结果场景，不收集商户密钥、证书或银行卡。真实签名、回调验签、金额核对、幂等、库存并发和资金对账需要服务端。
- 本地身份切换不是安全认证，localStorage 也不是生产权限或隐私隔离机制；仅使用虚构姓名、地址与订单。不要用于真实销售、医疗器械资质宣称或收款。
- 已通过 11 组隔离模拟校验：权限、商城入口、下单与库存、患者隔离、支付和配送、售后及申诉退款、取消、课程、历史快照、支付设置 / 持久化、临床数据隔离与旧页面回归。浏览器可视化及手机视口仍未验证；新增样式已按窄屏布局编写。
